# ADR-002: Frontend Stack — React, Vite, Tailwind, shadcn/ui

## Status
Accepted

## Date
2026-07-29

## Context
The rebuilt web application requires a modern, performant, and maintainable frontend. The UI must be responsive, accessible, themable (light/dark mode), and consistent with an editorial design system (refined typography, restrained accent color, generous whitespace). The team also wanted to minimize lock-in to a proprietary UI framework.

## Decision
Adopt the following frontend stack:
- **React 18** with **TypeScript** for the UI layer.
- **Vite** as the build tool and dev server.
- **Tailwind CSS** for utility-first styling.
- **shadcn/ui** primitives for accessible, composable components.
- **Lucide React** for icons.
- **Framer Motion** for subtle animations.
- **Recharts** for charts.
- **Zustand** for state management.
- **React Hook Form + Zod** for forms and validation.

## Alternatives Considered

### Next.js
- Pros: SSR/SSG, file-system routing, large ecosystem.
- Cons: Adds server complexity and deployment constraints; the project is primarily a client-side SPA with auth-gated dashboards.
- Rejected: A React + React Router SPA is simpler and aligns with the requested Vite stack.

### Material UI / Ant Design
- Pros: Comprehensive component sets, faster initial development.
- Cons: Harder to customize to an editorial brand; heavier bundle; more opinionated.
- Rejected: Tailwind + shadcn/ui gives full control over the design system while staying lightweight.

### Redux Toolkit
- Pros: Powerful debugging, predictable state updates.
- Cons: More boilerplate than needed for a medium-sized app; Zustand covers auth + UI state with less code.
- Rejected: Zustand is simpler and sufficient.

## Consequences
- Rapid styling iteration with Tailwind's utility classes.
- Consistent, accessible component patterns via shadcn/ui.
- The application can be deployed as static files, with API calls routed to the backend.
- Designers can adjust the editorial palette through CSS variables and Tailwind config.
