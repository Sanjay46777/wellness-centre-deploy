# ADR-003: Backend Architecture — Node.js, Express, and MySQL

## Status
Accepted

## Date
2026-07-29

## Context
The application requires a backend that handles authentication, role-based access control, CRUD operations, analytics aggregation, and export generation. The original Android app likely used Supabase for its backend. The rebuild keeps data on a normalized relational database with clear ownership and query control.

## Decision
Use:
- **Node.js** with **Express** for the HTTP server.
- **MySQL** as the primary relational database (via `mysql2` driver).
- **JWT** for stateless authentication.
- **Zod** for request validation.
- **Winston** for logging.
- **Helmet**, **CORS**, and **express-rate-limit** for security hardening.

## Alternatives Considered

### Supabase (existing mobile backend)
- Pros: Managed auth, database, and real-time subscriptions; reduces backend code.
- Cons: Ties the project to a managed platform; offline/self-hosting requirements; the requirement explicitly requested a custom Node.js/Express backend.
- Rejected: The project mandate is a custom REST API with MySQL.

### Django / Python
- Pros: Built-in admin, ORM, and security features.
- Cons: Team's primary stack is JavaScript/TypeScript; adds context switching and deployment complexity.
- Rejected: Node.js keeps the entire stack in one language and ecosystem.

### PostgreSQL
- Pros: Advanced features, strong JSON support, mature ecosystem.
- Cons: MySQL was explicitly requested; the data model is straightforward relational and MySQL handles it well.
- Rejected: MySQL matches the requirement and operational context.

## Consequences
- Full control over queries, indexes, and migrations.
- Clear separation between API routes and database logic.
- The team must manage database hosting, backups, and connection pooling.
- Authentication and authorization are implemented in-house using JWT.
