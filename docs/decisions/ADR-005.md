# ADR-005: Client-Side Rendering, Code Splitting, and Export Strategy

## Status
Accepted

## Date
2026-07-29

## Context
The application is a role-based SPA with many pages, charts, and heavy export libraries (PPT, PDF, Excel). Bundle size and initial load time are critical for a good user experience. The project must also support local development and preview without a running backend.

## Decision
- Render the application as a **client-side SPA** with React Router.
- Use **React.lazy** and **Suspense** to split pages into separate chunks.
- Load heavy export libraries (pptxgenjs, jspdf, xlsx) **on demand** inside the export handlers.
- Use a **mock API** in the frontend for development/preview when `VITE_USE_MOCK_API=true`.
- Fetch real data via Axios with a `VITE_API_BASE_URL` configuration.

## Alternatives Considered

### Server-side rendering (SSR) or static site generation
- Pros: Better initial page-load performance and SEO.
- Cons: Adds deployment complexity; most screens are behind auth and not public, so SEO is irrelevant.
- Rejected: CSR is simpler and sufficient for an authenticated dashboard app.

### Load all export libraries at build time
- Pros: Simpler imports, faster export button response.
- Cons: Adds ~1.5 MB to the initial bundle, even for users who never export.
- Rejected: Dynamic imports keep the initial bundle lean and load the export library only when needed.

### Use a single `export.ts` module
- Pros: One import statement, centralized logic.
- Cons: Any page that imports the shared module pulls all three heavy libraries.
- Rejected: Split the export code into `export-ppt.ts`, `export-pdf.ts`, and `export-excel.ts` so each format is loaded independently.

## Consequences
- First page load is faster, especially on slower networks.
- Export buttons show a small delay the first time they are clicked while the library chunk downloads.
- Developers can test the full UI with mock data without a database.
- The build output is optimized for static hosting and CDN caching.
